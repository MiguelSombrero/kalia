# ADR-0094: The mobile app is Expo as a development build with generated native projects and no paid service

- **Status:** accepted
- **Date:** 2026-10-30

## Context

Iteration 9 adds a second client, and every build task in it inherits the
stack this decision picks. The [roadmap](../roadmap.md) already names Expo and
the [backlog](../tasks/backlog.md#mobile-client) gives one reason for it:
over-the-air updates soften the cost of a client that cannot be redeployed in
lockstep with the server. Nothing recorded why Expo rather than Flutter or two
native apps, or which of Expo's modes Kalia runs in, and the modes differ in
what they cost.

Three forces decide it. The app must carry its own redirect scheme,
`kalia://`, for the sign-in that [task 05](../tasks/iteration-9/05-decision-mobile-authentication.md)
decides. The project adds no cost and puts no payment card on file anywhere:
no paid account, cloud build, hosting or billed CI minute, and anything that
needs one is parked in the backlog until the product owner decides to spend.
And [ADR-0092](0092-the-repository-is-plain-npm-workspaces-of-web-mobile-and-two-packages-that-ship-typescript-source.md)
has already made the generated API client and the en/fi strings TypeScript
packages that the app consumes, so a language other than TypeScript would
forfeit them.

Expo and React Native postdate model training, so every statement about Expo
below is from the official documentation, read on 2026-10-30 (Evidence), not
from memory.

Product-owner decisions at refinement on 2026-10-30, recorded here as made.

## Decision

**The mobile app is an Expo app built as a development build, with `ios/` and
`android/` generated by `expo prebuild` and never committed, Expo Router for
navigation, TypeScript in strict mode, and no paid service anywhere on its
build or run path.**

- **A development build, not Expo Go.** The app is compiled with Expo's
  development client and run on the iOS Simulator and the Android Emulator.
  Expo Go is not used, because it cannot carry the `kalia://` scheme.
- **Continuous native generation.** `ios/` and `android/` are generated by
  `expo prebuild`, are gitignored, and are regenerated rather than edited.
  `app.json` and config plugins are the source of truth for everything native;
  a fresh clone generates the projects through [task 10](../tasks/iteration-9/10-developer-environment.md)'s
  `make` targets.
- **Expo Router,** and TypeScript with `strict` on, as the web has it.
- **Minimum OS versions are the chosen SDK's own,** not raised: Kalia has no
  feature that needs a newer floor.
- **The SDK version is not decided here.** It is asked in
  [task 11](../tasks/iteration-9/11-app-skeleton.md)'s one batched dependency
  question and recorded in `mobile/package.json` only. Runtimes follow
  long-term support ([ADR-0085](0085-runtimes-follow-long-term-support-not-the-newest-major.md)),
  and the Node the app's tooling runs on is the repository's.
- **The web's conventions carry over by pointer:** TanStack Query behind
  feature-owned hooks ([ADR-0008](0008-tanstack-query.md),
  [ADR-0041](0041-tanstack-query-feature-owned-hooks.md)), Zustand for client
  state ([ADR-0009](0009-zustand-ui-state.md)), react-hook-form with Zod
  ([ADR-0010](0010-react-hook-form-zod.md)) and i18next with Finnish a full
  peer of English ([ADR-0011](0011-i18next-localization.md)). Those ADRs are not
  amended. What in them is about the browser (locale-prefixed URLs, Server
  Actions as the read path, [ADR-0040](0040-client-reads-via-server-actions.md))
  does not apply to the app, and how the app reaches the API is task 05's. No
  other web ADR is adopted by this one.
- **Plain `StyleSheet` until [iteration 11](../tasks/iteration-11.md)** decides
  the design language and the token format. A styling library chosen now would
  pre-empt that decision.
- **No part of the build or run path needs a paid account.** Building uses
  `expo run:ios` and `expo run:android` on the developer's machine against a
  simulator or emulator, and no Expo account is involved. Adopting any of the
  following would break that, and each needs the product owner's decision to
  spend first: EAS Build, which runs in Expo's cloud and, even as
  `eas build --local`, needs an Expo login; EAS Update, the cloud service that
  serves over-the-air updates; the Apple Developer Program, which Expo's setup
  guide requires to install a development build on a physical iPhone; and
  store distribution. The app is therefore verified on simulators, as the
  iteration's goal says, and a physical device is out of scope until that
  decision is made.

## Alternatives considered

- **Expo Go.** Zero native toolchain: scan a code and run. Rejected because
  it does not use the app's custom scheme (it opens projects on `exp://`), so
  the `kalia://` redirect cannot land in it, and because it cannot run
  libraries with custom native code. Expo's own FAQ calls it a playground and
  recommends development builds for any real project.
- **Flutter.** Dart and its own toolchain, CI job and test runner. It could
  consume none of the TypeScript packages of ADR-0092, so the API client and
  the strings would be generated or copied a second time, the drift that ADR
  was written to remove; and none of the web's conventions (TanStack Query,
  Zod, i18next) would carry. The price is a second language for a team of one
  reviewer.
- **Two native apps (Swift and Kotlin).** The same objection twice over: two
  more codebases, each with its own toolchain, none of them sharing a line
  with the web, and every feature built and reviewed twice.
- **Bare React Native without Expo.** Keeps TypeScript and the shared
  packages. Gives up what Expo's tooling does for the native projects:
  `ios/` and `android/` would have to be committed and maintained by hand, and
  every React Native upgrade becomes a native diff to merge by hand, which is
  the cost the next option names.
- **Commit `ios/` and `android/`.** Rejected by the
  product owner: every SDK upgrade becomes a large native diff in a pull
  request, and hand edits drift from `app.json`, so two files claim to say the
  same thing. Expo's documentation warns of the same loss: manual edits are
  lost on `prebuild --clean`.
- **EAS cloud builds and updates.** The easy way to produce signed builds and
  to ship JavaScript changes without a new install. Rejected because they are
  a paid service beyond a small free allowance (Evidence), and the project
  adds no cost. The over-the-air argument in the backlog's mobile analysis
  therefore does not hold for Kalia, and the compatibility discipline of
  [ADR-0093](0093-the-api-is-additive-only-while-an-app-is-installed-and-a-committed-spec-fails-a-breaking-diff.md)
  is what covers an installed app that cannot be updated at once.
- **React Navigation without Expo Router.** Routes and navigators are defined
  by hand in code, where Expo Router derives them from the files in `app/`.
  Rejected: more code to keep in step with the screens for no capability the
  app needs.
- **A styling library now** (a utility-class or component library). Rejected:
  it would fix the token format before iteration 11 has designed anything.
- **Raise the minimum OS versions** above the SDK's. Rejected: it shrinks the
  set of devices that can install the app without buying a feature.

## Consequences

- Good, because the app, the web and the shared packages are one language, so
  the generated client, the strings and the conventions are consumed rather
  than rewritten.
- Good, because `app.json` and config plugins are the only place a native
  setting lives, so there is no second copy that can disagree.
- Good, because nothing on the build or run path needs an account, and the
  project's no-cost rule holds for the app without an exception.
- Bad, because every developer machine needs the native toolchains: Xcode for
  iOS and Android Studio with a JDK for Android. The environment is
  [task 10](../tasks/iteration-9/10-developer-environment.md)'s to make
  repeatable, and a machine without them cannot run the app.
- Bad, because a fresh clone has no `ios/` or `android/` until prebuild runs,
  and a change to `app.json` or a config plugin (the scheme included) needs
  a new development build, not a reload.
- Bad, because there is no over-the-air path: a JavaScript-only fix reaches a
  device only as a new build, and the backlog's softening argument is not
  available.
- Bad, because an SDK upgrade can break a config plugin or the generated
  native projects, and the break shows at prebuild or in the native compile
  rather than in TypeScript.
- Neutral, because plain `StyleSheet` styling written now is rewritten when
  iteration 11 chooses a token format.
- Neutral, because a physical device is unverified until the product owner
  decides to pay for what installing on one needs.
- **Revisit trigger:** the product owner decides to spend (EAS, a developer
  account or a store release), or the app needs a native module the config
  plugins cannot express.

## Evidence

Read in Expo's official documentation (docs.expo.dev and expo.dev/pricing) on
2026-10-30. **Read, not run:** no `mobile/` exists yet, and
[task 11](../tasks/iteration-9/11-app-skeleton.md) confirms each point below
by building it. No SDK version is recorded here, deliberately; the documentation
read was the current one, and the chosen SDK's own pages are what
task 11 checks.

- Expo Go runs a project's JavaScript inside a prebuilt app, so custom native
  code cannot be added; the FAQ says it "cannot use third-party libraries that
  require custom native code" and calls it "a playground for students and
  learners".
- The linking guide says Expo Go "uses the `exp://` scheme" by default, and
  that a custom `scheme` in the app config needs "a new development build".
  Whether Expo Go can be made to accept a custom scheme is not stated outright;
  the rejection above rests on this wording.
- A development build is the app compiled with the `expo-dev-client` library,
  and `npx expo run:android` or `npx expo run:ios` builds one locally, needing
  "your native toolchain and no Expo account". The same page calls this "the
  only way to install a development build on an iPhone without a paid Apple
  Developer account". The setup guide says the opposite for a physical iPhone:
  it needs "an active subscription to the Apple Developer Program". The pages
  disagree, so this ADR relies on neither, and scopes the verified path to
  simulators. Neither page says whether the simulator needs an Apple account.
- Continuous native generation: `expo prebuild` generates `ios/` and
  `android/` from a template for the SDK version, then applies config plugins;
  the directories "are automatically added to .gitignore when you create a new
  project"; editing them risks losing the changes "the next time you run"
  `prebuild --clean`.
- `eas build --local` needs `eas login` or an `EXPO_TOKEN`; the build runs on
  the developer's machine and EAS is contacted only to confirm the project and
  to fetch managed credentials.
- EAS Update is described as "a cloud service from EAS"; the page read does not
  describe a self-hosted alternative, so none is relied on.
- The pricing page lists a free plan at $0 with "Up to 15 Android and 15 iOS
  builds" at low priority, and paid plans from $19 a month plus usage. The page
  does not say whether the free plan asks for a payment card, so the free tier
  is not used as a way around the rule.
- Expo Router is "a file-based router for React Native and web applications":
  a file added to the `app` directory becomes a route, and every screen is
  deep-linkable.
- The TypeScript guide's own example extends `expo/tsconfig.base` and adds
  `"strict": true` to `compilerOptions`, and does not present strict mode as
  the default, so enabling it is part of task 11.
