# CI failure playbook

A lookup table from **a red check** to **the document that already explains
the fix**. Nothing here is the fix itself: each entry points at the ADR or
README that owns it, because a second copy of a rule is the drift
[ADR-0020](adr/0020-documentation-roles.md) exists to prevent. What this file
adds is the mapping — a failing job name is not something you can grep the
docs for, and the recurring cost was never *understanding* these failures but
*recognising* them.

**This is a document, not a backlog of scripts.** A checker per failure was
proposed once and rejected by the product owner: a standalone script
enforcing one dependency's version agreement doesn't generalize, and "a
script per dependency isn't sustainable" (`c408b36`). The checkers that do exist guard whole classes
([ADR-0039](adr/0039-mechanisms-for-recurring-rule-violations.md)); a
signature that does not fit one of those belongs here instead.

Add an entry when a failure costs you more than a couple of minutes to
recognise, and only once it has actually happened — a speculative signature
is a guess with a table row around it. Say which run it came from.

## API client drift check

**Every generated file differs, by the header line only.** An `orval` bump
changed what it stamps into the header. 8.23.0 → 8.24.0 dropped the version
from `Generated by orval v8.23.0 🍺`, and all 21 files drifted at once with
no API change (`7079412`). Regenerate, then confirm the diff really is
header-only before committing — that check is what distinguishes this from a
genuine contract change.

**A bigger orval bump changes the generated code shape, not just the header.**
8.24.0 → 8.37.0 added a `getXMutationKey()` helper and a named
`XMutationVariables` type per mutation, and normalized request headers
through a new `getHeaders()` inliner — every file with a mutation hook
changed, still with no API change ([PR #302](https://github.com/MiguelSombrero/kalia/pull/302)).
Same fix as above: regenerate, then read the diff to confirm it is orval's
own output shifting, not a contract change, before committing.

**One endpoint loses its success response.** Adding any `@ApiResponse` to a
handler — including one declared at the class level — makes springdoc stop
synthesising the success response from the return type, and drop it from
`/v3/api-docs` rather than add to it. There is no compile error and no test
failure. The rule, and the `@ResponseStatus` that fixes it, is in
[backend/README.md](../backend/README.md)'s conventions.

Run it locally before pushing either way: `make api-drift` (it regenerates from
`backend/openapi.json`, needing neither Docker nor a backend). An orval bump is
`npm run generate --workspace @kalia/api`, then the same read of the diff.

## Frontend (npm) — lint

**`eslint-plugin-boundaries` rejects an import, often in a *new test file*.**
Test files are subject to the layer rules like any other file. The layers,
the directions allowed between them, and the feature-barrel rule that makes
`features/catalog/BeerList` illegal where `features/catalog` is fine, are in
[web/README.md](../web/README.md)'s conventions; the choice of that
plugin and the verification of each rule is
[ADR-0012](adr/0012-orval-api-client.md).

`make verify-fast` runs this lint, so a pre-push hook catches it.

## Static checks — `check-comments.mjs`

**A comment names a task, an iteration, a PR, or how the code used to be.**
Those patterns hard-fail, in `mobile/src` and `scripts/*.mjs` too; the ratio and ADR-block
findings are advisory, never fail, and print only with `--advisory`. Delete the narration — the policy and its test are
`.claude/rules/code-comments.md` and
[ADR-0017](adr/0017-code-comment-policy.md).

## Static checks — `check-adrs.mjs` / `check-tasks.mjs` / `sync-indexes.mjs`

The checker output names the file and the missing thing; it is precise enough
to act on directly. **"An index cell disagrees with the file it mirrors"** is
fixed by `make sync-indexes`, never by editing the cell
([ADR-0076](adr/0076-index-cells-are-synced-from-their-files.md)); it means the
file changed somewhere the edit-time hook did not run. The one failure it cannot phrase helpfully is a **number
collision**, which arrives as a merge conflict in
[architecture.md](architecture.md)'s ADR index rather than as a checker
message: two branches each claimed the next number, because each read only
its own working tree. Renumber whichever has not merged, and allocate with
`make next-adr` — which scans every remote-tracking ref, for exactly this
reason ([ADR-0046](adr/0046-edit-time-checks-and-one-verify-gate.md)).

## E2E (Playwright)

**`Error: Timed out waiting 300000ms from config.webServer` — no test ran.**
Not a test failure: Playwright's `webServer` starts `docker compose up --build`,
and a cold CI runner has no BuildKit cache, so the frontend image's own
`npm ci` alone takes 3–5 min (slow-registry days) before `next build` and the
stack's containers come up healthy. The 5-minute default overran on `dev` itself
(runs `33842075895`, `33838096364`) and on PR #219. The wait budget lives in
`frontend/playwright.config.ts`'s `webServer.timeout` — raised to 12 min. If it
still overruns, the build itself is the thing to speed up (layer-cache the
image in a CI step, then `docker compose up` without `--build`), not the timer.

**`Error: Process from config.webServer was not able to start. Exit code: 1`
— no test ran.** This is the same `docker compose up --build` failing outright
rather than slowly. The cause is in the `[WebServer]` lines above it, not in
Playwright's message. Search the log for `BUILD FAILURE`. One cause seen so
far is the backend image's `mvn -B dependency:go-offline` failing with `Could
not transfer artifact …` from Maven Central: a transient registry failure,
unrelated to the diff. A Markdown-only PR hit it in run `38698155228`. Re-run
the failed job (`gh run rerun <id> --failed`). Fix something only if the same
artifact fails again, because then the cause is the dependency, not the
network.

**`Process from config.webServer was not able to start`, and the
`[WebServer]` lines end in `failed to resolve source metadata for
quay.io/keycloak/keycloak:… 503 Service Unavailable`.** quay.io was down
while the `keycloak` image's `FROM` was resolved; one outage turned the E2E
job red on three PRs: runs `40059787067` (#386), `40061839941` (#390) and
`40062800899` (#392). The E2E and Keycloak realm jobs now run a
`Pre-pull compose images` step first, retried three times like the backend
job's, and a build whose base image is already local does not contact the
registry. If that step itself exhausts its three attempts, the registry is
still down: re-run the failed job once quay.io's status recovers
(`gh run rerun <id> --failed`), and change nothing in the diff.

**Several registration specs time out waiting for `#username`, each passes in
isolation, and which ones fail moves between runs.** The shared `/sign-up`
rate limit is spent. It is one counter for every visitor, by design
([ADR-0055](adr/0055-self-registration-via-keycloak.md)), and a full suite run
spends about five attempts. Nothing expired them between runs, so several consecutive `npm run test:e2e` runs exhausted the window — and
once it is exhausted the Server Action redirects to
`/sign-up?error=rate-limited` instead of Keycloak, so the specs never reach a
registration form and fail on the `#username` wait with nothing in the trace
naming a rate limit. Observed locally with the counter standing at 36; a
`docker compose exec valkey valkey-cli del auth:sign-up-rate` from the repo
root turned the same run 38/38 green. The suite now clears the counter before
every test that uses the shared `test` fixture — how, and what a spec has to
do to opt in, is in [web/README.md](../web/README.md). That `del` is
still the one-line escape hatch if a spec ever registers outside it.

**After clicking Sign out, `Sign in` never appears; the snapshot still shows
the signed-in header (and maybe a loading skeleton), and the call log says
`waiting for http://localhost:3000/en navigation to finish`.** Not a slow
Keycloak: the click landed before the page hydrated, so the browser posted
the Server Action form natively — `multipart/form-data`, no `Next-Action`
header — and `form-action 'self'` blocked its redirect to Keycloak (*"Sending
form data to 'http://localhost:3000/en' violates … form-action 'self'"* in
the console). The local session is gone by then and Keycloak's is not, and
the page never moves. Measured 7 failures in 16 on `sign-up.spec.ts`'s "sign
in again" (`--repeat-each=8`, `445984f`, 2026-10-04), plus one in a full
`make verify`; forced every time by delaying `/_next/static/chunks/**/*.js`.
The auth buttons are now disabled until hydration, so Playwright's click
waits for them — a recurrence means a cross-origin Server Action form has a
plain submit button again ([web/README.md](../web/README.md)'s
traps, [ADR-0025](adr/0025-authjs-valkey-adapter.md)'s 2026-10-04 amendment).
Raising the expect timeout does not help: nothing is still in flight.

**Under `--repeat-each`, a registering spec lands back on Kalia signed out
— `getByRole('link', { name: /^Profile: / })` not found — while other
copies of the same test pass.** Two copies picked the same timestamped
username in the same millisecond. In the trace, the loser's registration
`POST` answers `200` (the form re-rendered: username taken) rather than `302`
to `VERIFY_EMAIL`, yet its Mailpit lookup finds the winner's message; opening
that link in a browser with no Keycloak auth session ends on an info page
whose "Back to application" goes to `/` signed out (observed 2026-10-04: 4
of 8, then 1 of 8). Registering specs name accounts with `uniqueUsername`
(`frontend/e2e/support/keycloakAccount.ts`); a new one that uses a bare
`Date.now()` brings this back.

**A spec fails only against a brand-new stack (`docker compose down -v`), and
passes once other specs have run.** It depends on data another spec leaves
behind. Observed 2026-10-11 in `shell.spec.ts` run alone on an empty database:
`getByRole('link', { name: 'Create an account' })` hit a strict-mode
violation, *resolved to 2 elements*, the second under `#main-content`. An empty
front-page feed renders its own sign-up link beside the header's, so the
checks were reliable only once the feed had entries. Scope a shell assertion to
`getByRole("banner")`; reproduce by running the one file right after
`down -v && make up`.

**A short page's height check fails with `scrollHeight` 907 against an
800-pixel window, and passes on a rerun.** It measured the loading skeleton:
the first request to a route after the frontend starts can resolve `goto`
while one or two skeleton `<main>`s are still in the DOM, and the page's own
content arrives later. Traced 2026-10-11 on `/en/beers/<unknown id>` by
restarting the frontend container before each run. Wait for something only the
settled page has, such as its `<h1>`, before measuring layout.

**`profile-visibility.spec.ts` fails `toBeChecked()` on "Anyone with the
link" right after `page.reload()`, and passes on a rerun.** The spec reloaded
while the visibility save was still in flight. `VisibilityControl` updates
optimistically, so its confirmation text is visible 11–43 ms before the
Server Action's `POST` returns, and which request the backend served first
decided the outcome. It flaked about one run in three, across six PRs before
anyone diagnosed it; fixed in [PR #328](https://github.com/MiguelSombrero/kalia/pull/328)
by saving through `setCellarVisibility` (`frontend/e2e/support/visibility.ts`),
which waits for the `POST`. A recurrence means a spec toggled visibility and
reloaded without that helper. Separately, axe once reported `document-title`
on the profile page right after a save and has not been reproduced since;
without a second occurrence there is no signature to write down.

## Vulnerability scan

**Red on a CVE that has nothing to do with your diff.** Expected, and by
design: the scan is diff-agnostic, so any open PR can go red the moment a CVE
is disclosed against something already in `dev`
([ADR-0024](adr/0024-dependency-vulnerability-scanning.md)). It is fixed in
place on the branch that is open, not in a second PR. Whether it needs asking
first is in the `implement-task` skill's "A red check"; `make trivy-scan`
reproduces the manifest scan, and the image scan's invocation is in
`backend/README.md`.

## Not CI, but the same recognition problem

**The backend will not boot after pulling `dev`, complaining about a Flyway
checksum.** Your local Postgres volume ran an earlier version of a migration
that has since been edited. This is routine rather than exceptional, and the
fix is in [backend/README.md](../backend/README.md) database migrations
([ADR-0036](adr/0036-pre-deployment-migration-edits.md)).

**A `make` target that runs `docker compose up --wait` exits `1` although
every container is fine.** `--wait` on a one-shot (`keycloak-config`,
`keycloak-seed`) races: Compose exits `0` if it sees the container before it
finishes and `1` ("exited (0)") if it has already gone, and `keycloak-config`
finishes in under a second. Measured on Compose v5.5.1, 2026-10-25, by
repeating `up -d --wait keycloak-config` against one stack. Name only
long-running services in a `--wait` invocation; run a one-shot with
`docker compose run --rm <service>`, which waits for it and returns its own
exit code, or let the script that consumes it retry (each
`scripts/check-keycloak-*.mjs` has its own retry loop). Cost ~10 min to spot
on the branch for iteration 6.5 task 03, because the failing line had been
piped to `tail` — which also hid it (see `implement-task` step 9: read `make`
output from a file, not a pager).

**`make verify` fails at `frontend-build` with a TypeScript error in a file
your diff never touched.** In a newly created worktree, `frontend/node_modules`
does not arrive in a state matching `package-lock.json` — `git worktree add`
does not populate it, and a copied or previously-installed tree can be several
bumps behind. The symptom is a type error, not a version complaint:
`vitest.setup.ts(14,13): error TS2428: All declarations of 'Matchers' must have
identical type parameters`, because that file re-declares vitest's `Matchers`
for `jest-axe` against vitest 5's type shape while vitest 4 is what is actually
installed. `npm test` passes throughout and prints `RUN v4.1.10` — that banner,
compared against the lockfile, is the tell. Run `(cd frontend && npm ci)` before
the first `make verify` in a fresh worktree. Observed 2026-09-19 on the branch
for this file's sign-up rate-limit entry above.

**`mvn` fails to compile the backend with
`java.lang.ExceptionInInitializerError: com.sun.tools.javac.tree.EndPosTable`.**
Lombok meeting a JDK newer than the one the build targets. `mvn` reads
`JAVA_HOME`, which on a Mac with several JDKs installed is whichever one is
first on the path — not necessarily the version `java -version` reports, and
not necessarily `pom.xml`'s release. The pin is in
[backend/README.md](../backend/README.md). The error names
javac's internals rather than a version mismatch, and an *incremental* build
that recompiles nothing at all skips it entirely — so a target can pass once
and fail the next time without the tree changing.
