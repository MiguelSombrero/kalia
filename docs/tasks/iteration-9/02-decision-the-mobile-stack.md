# Task 02: Decide the mobile stack

- **Status:** needs-refinement
- **Iteration:** [9](../iteration-9.md)
- **Covers:** DW-5

## Why

Iteration 9 builds a second client, and every build task in it inherits the
stack this one chooses. The [roadmap](../../roadmap.md) already names Expo, and
the [backlog's mobile analysis](../backlog.md#mobile-client) gives a reason for
it — over-the-air updates soften the cost of a client that cannot be redeployed
in lockstep — but nothing records why Expo rather than Flutter or two native
apps, or which of Expo's several modes Kalia runs in. Those modes differ in
what they cost: Expo's paid cloud builds would break the plan's no-cost
constraint, and Expo Go cannot carry a custom `kalia://` redirect scheme.

## Scope

The mobile stack is a recorded decision: the framework, how the native
projects are built and whether they are committed, the router, the language
settings, and which of the web's conventions carry over as they are.

## Non-goals

- The mobile design language and how tokens are shared —
  [iteration 11](../iteration-11.md).
- Building anything: [task 11](11-app-skeleton.md) builds what this decides.
- Repository layout — [task 03](03-decision-repo-layout-and-code-sharing.md).

## Constraints

- The plan adds no cost and puts no payment card on file
  ([backlog](../backlog.md#mobile-client)): nothing chosen may depend on EAS's
  paid cloud builds or updates.
- New dependencies: name them and ask which versions, in one batched question
  (`CLAUDE.md` "New dependencies: ask, don't research").
- [ADR-0085](../../adr/0085-runtimes-follow-long-term-support-not-the-newest-major.md):
  runtimes follow long-term support, not the newest major.
- The output is an ADR to [the template](../../adr/template.md), with the
  rejected options recorded
  ([ADR-0019](../../adr/0019-adr-format-and-conventions.md)).

## Open questions

1. **Expo with a development build, confirmed?** The planned line chooses it
   over Expo Go; the ADR needs the rejected alternatives costed — Flutter, two
   native apps, bare React Native without Expo.
2. **Are `ios/` and `android/` committed, or generated by `expo prebuild` and
   gitignored** (continuous native generation)? It decides what a reviewer
   sees in a diff and what a fresh clone has to run before the app builds.
3. **The minimum iOS and Android versions** the app supports — they bound which
   simulators and emulator images [task 10](10-developer-environment.md)
   installs.
4. **Which Expo SDK**, and therefore which React Native and React — a version
   question for the product owner, asked once for the whole stack.
5. **Which web conventions carry over unchanged?** [Task 11](11-app-skeleton.md)
   assumes TanStack Query behind feature hooks, Zustand, react-hook-form with
   Zod and i18next ([ADR-0008](../../adr/0008-tanstack-query.md) to
   [ADR-0011](../../adr/0011-i18next-localization.md),
   [ADR-0041](../../adr/0041-tanstack-query-feature-owned-hooks.md)). Do those
   ADRs widen to cover mobile, or does this ADR adopt them by pointer?
6. **Styling without a design language yet** — plain `StyleSheet` until
   [iteration 11](../iteration-11.md) decides, or a styling library chosen now
   that iteration 11 then inherits?

## Acceptance criteria

- [ ] An ADR records the stack, the rejected alternatives and what each would
      have cost, and passes `node scripts/check-adrs.mjs`
- [ ] The ADR states that no part of the build or run path needs a paid
      account, and names what would break that if adopted later
- [ ] `docs/architecture.md` §2 names the mobile client and its stack
- [ ] The tests the decision implies — the unit-test runner and the native
      end-to-end tool's place in the build — are named in the acceptance
      criteria of tasks [11](11-app-skeleton.md) and
      [15](15-walking-skeleton-slice.md) before either is refined
